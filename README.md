# 在线分片扩容迁移工具（4 → 16，SQLite 模拟）

业务库按用户 ID 取模分了 4 个分片，需要在线扩容到 16 个分片，**全程不停机**。
本项目用 SQLite 文件模拟物理分片库，实现一套完整的在线扩容迁移工具与迁移控制台，
并提供一个持续读写的压测脚本做端到端验收。

纯 Python 标准库实现（`sqlite3` / `http.server` / `threading` / `hashlib` / `heapq`），
无任何第三方依赖。

## 目录结构

```
shard_mig/
  sharding.py   新旧分片规则与双向定位（uid % 4 / uid % 16）
  cluster.py    分片集群：SQLite 文件、业务表、变更日志/回滚日志、分片锁
  gateway.py    业务读写网关：模式切换、全局 gseq、手机号唯一、对照库镜像
  migrator.py   迁移引擎：搬运 / 追平 / 校验和 / 切换 / 回滚 状态机
  console.py    迁移控制台：HTTP API + 内嵌单页 UI
app.py          独立启动控制台（人工操作）
stress_test.py  端到端压测与验收脚本
```

数据目录（默认 `run_demo/`）：

```
old/old_shard_00..03.db     旧 4 分片（含 changelog 变更日志）
new/new_shard_00..15.db     新 16 分片（含 rollback_log 回滚日志）
coordinator.db              协调库：全局 gseq 序列、手机号注册表、网关模式
control.db                  不迁移的对照库：每次成功写入同步镜像，最终正确性基准
```

## 快速开始

### 一键端到端压测（推荐，自动验收）

```bash
py stress_test.py --data-dir run_demo --seed 10000 --duration 25
```

全部满足才退出码 0：

- 最终新库数据与对照库 `control.db` **逐行一致**；
- 切换/回滚期间**不可写时间 < 3 秒**；
- 任意时刻新库**无跨分片重复手机号**；
- 分段校验和最终**全部段一致**；
- 回滚后旧库与对照库一致（**回滚期间新数据不丢**）。

常用参数：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--seed` | 10000 | 预置存量用户数 |
| `--workers` | 6 | 业务并发线程数 |
| `--duration` | 25 | 切换前持续读写秒数 |
| `--rate-limit` | 3000 | 搬运限速（行/秒，0=不限） |
| `--readonly-hold` | 1.0 | 注入只读保持秒数，用于确定性测量不可写时间 |

> `--readonly-hold 0` 时为真实切换速度，实测只读窗口 25~140ms；
> 压测默认注入 1.0s，保证业务线程能采样到只读拒绝，从而验证 < 3s 指标。

### 人工操作控制台

```bash
py app.py --data-dir run_demo --port 8765
# 浏览器打开 http://127.0.0.1:8765/
```

控制台五个分区对应需求：**① 分片规则 ② 迁移计划 ③ 数据搬运 ④ 增量追平 ⑤ 切换与回滚**，
状态每秒自动刷新，可在线调整限速、暂停/恢复、发起校验、切换与回滚。

## 核心设计与七项需求的对应

### 1. 新旧分片规则并存，双向定位

`sharding.py`：旧规则 `uid % 4`、新规则 `uid % 16`。
`locate_both(uid)` 同时算出一个用户在旧库和新库的物理位置。
扩容映射：旧分片 `k` 的数据拆到新分片 `k, k+4, k+8, k+12`。

### 2. 存量数据分批搬运，限速，不影响线上读写

- 后台 `backfill` 线程按旧分片、按主键游标分批读取（默认每批 500 行）；
- `RateLimiter` 令牌桶限速，控制台可动态调整；
- 搬运走 `replay_upsert`，带 **gseq 版本守护**（`WHERE excluded.gseq > users.gseq`），
  旧版本不会覆盖追平线程已写入的新版本；
- 搬运只写新库，不碰线上旧库，业务读写不受影响；支持暂停/恢复。

### 3. 变更日志增量追平，直到两边几乎一致

- 每次在线写入在分片内**同事务**写业务行 + `changelog` 变更日志，携带全局单调 `gseq`；
- 后台 `catchup` 线程把 4 个旧分片的 changelog 按 gseq 归并（`heapq.merge`），
  按全局顺序重放到新库，追平滞后量 `lag` 实时可见；
- 切换前在只读窗口内 `drain_catchup` 把增量追到 `lag=0`。

### 4. 切换时短暂只读，秒级完成，切完走新规则

切换流程（`switch_to_new`）：

1. 写锁内**瞬间**进入只读（读仍走旧库，写立即收到 `ReadOnlyError`）；
2. 停止后台追平线程，本流程独占 drain，追到 `lag=0`；
3. 只读窗口内做最终分段校验，强制收敛到全绿；
4. 手机号跨分片重复终检 → 安装分片内唯一索引；
5. 写锁内**瞬间**切到新规则，恢复读写。

模式翻转在锁内是纳秒级，只读窗口实测几十到一百多毫秒，远小于 3 秒。

### 5. 一键回滚，回滚期间新数据不丢

- 切换后新库承载写入，每次写在同事务记录 `rollback_log`；
- 回滚先进入只读，再把 `rollback_log` 按 gseq 序**反向回放**到旧库
  （`replay_*` 只改业务表、不写 changelog，杜绝回声变更）；
- 回放完成才切回旧规则。回滚期间的写入先被只读挡住、随后全部落到旧库，**零丢失**；
- 支持回滚后重新切换（`reswitch`），可重复执行。

### 6. 按主键分段校验和，逐段比对，不一致段重搬

- 以旧库全量有序主键按固定行数（默认 1000 行/段）切分段边界；
- 每段对新旧库跨分片归并后的规范化行算 SHA-256，逐段比对；
- 不一致段整段重搬：旧库存在的行做版本守护 upsert，新库多出的残留行物理删除；
- **两阶段校验**：在线预检容忍在途写入差异（不硬失败）；
  切换只读窗口内无新写入，`final_verify` 循环重搬到全部段一致，保证切换点强一致。

### 7. 跨分片手机号唯一约束

三层保障，迁移过程中不出现重复：

1. 协调库 `phone_registry` 全局注册表，写入前判定归属，冲突抛 `PhoneConflictError`；
2. 旧库分片内 `phone` 唯一索引始终在线；
3. 新库迁移期由全局注册表 + 切换前跨分片重复扫描兜底，
   校验干净后才安装分片内唯一索引，承载切换后的在线约束。

## 关键并发正确性说明

- **全局 gseq**：协调库单序列分配，所有变更日志按 gseq 全局定序，重放顺序确定；
- **分片锁**：每个 SQLite 连接配一把锁，读写事务在该分片上串行，
  杜绝多线程共用连接导致的事务交错；
- **连接 autocommit**：`isolation_level=None`，事务边界完全由代码 `BEGIN/COMMIT` 控制；
- **日志同事务**：业务行与日志行在同一事务写入，移除了 trigger + 上下文表的隐式脆弱方案；
- **对照库镜像**：每次成功写入在同一把写锁内同步镜像到 `control.db`，顺序与业务严格一致。

## 阶段状态机

```
IDLE → BACKFILLING → BACKFILL_DONE → VERIFIED → SWITCHED
                                   ↑          ↓
                               ROLLED_BACK ← ROLLBACK
（任意阶段异常 → FAILED，事件日志保留现场）
```
